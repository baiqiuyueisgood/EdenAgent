# 群文件引用与艾特收件

日期：2026-10-14。用户要求群友先发送文件，再回复该文件消息并 @智能体，作为群智能体的文件输入。

## 实现行为

群成员先上传文件，再在 QQ 中引用该文件消息并明确 @机器人；可同时写处理要求，没有额外文字时默认请求查看并概述文件。只上传文件不会触发下载或自动拼接下一条群消息。同群成员可以引用其他成员上传的文件，实际提问者仍是引用消息的发言人。

- BotCore 从原始消息中的 @ 和回复 ID 识别收件意图；已知的普通文字、图片引用沿用原聊天。对文件引用使用 NapCat `get_msg` 重新核对原消息类型、群号与消息 ID，不使用用户提供的 URL 或本地路径作为下载入口。
- 原消息中的文件必须有合法文件 ID、文件名和明确大小；单文件不超过 100 MB（100,000,000 字节），每次最多 4 个。撤回、缺失、跨群、私聊或无效文件的引用明确失败，不伪装成已读取。
- 下载前通过现有 `accessCheck` 查询 Core 的新增 `group_agent` 能力，复用群开启、群准入及成员黑名单规则；不能凭普通群聊天权限下载智能体附件。实际下载复用 NapCat 的接收文件缓存读取，校验普通文件、长度和上限。
- BotCore 提取共用输入上传步骤到 `qq_file_upload.py`，保留私聊文件与图片的原读取方式。群分块绑定机器人连接、本次请求、群、真实发言人、引用回复消息及原文件消息，单帧沿用 96 KiB 块。
- Core `group_file_input.py` 校验引用来源、明确 @ 和上述绑定，再核对附件文件名及长度；上传完毕后重新读取群授权。群输入不会调用私聊 `stage_files`。
- Agent 群桥接新增 `qq-group-turn.v2` 附件输入，要求引用原消息 ID；v1 文字回合兼容，v1 不能夹带文件。附件经过有界存储与快照校验进入该群、该发言人的本次持久输入，重复消息还校验附件一致性。
- 群工具目录只额外开放 `read_attachment`，仍不能读本地工作区、执行命令、读取其他输入或私聊附件。附件工具按活动输入与会话绑定读取，100 MB 文件的分页偏移同步到文件上限。群会话最终输出不公开私聊审批和文件导出详情。
- 群模式管理和群写操作继续遵循上一项权限修正；普通成员没有借用个人超级管理员权限。最终文本及图片下发前继续重查群授权。

协议只增加附件输入版本，不改变数据库 schema 或 Mon 正式产品版本。引用消息 ID 留在受信桥接协议，不进入模型提示；模型只获得正常附件选择和分页读取接口。

共 291 项通过。新增 Agent 用例使用实际 100,000,000 字节文件，经签名 HTTP 上传、群桥接、持久输入、实际模型工具调用和附件分页读取，确认可以读到文件最后 16 字节；验证模型看得到附件工具而看不到本地文件工具。另验证私聊暂存队列没有被群提问消费，其他发言人的活动输入不能读取该文件，旧回合完成后不能继续读取，重复消息不新增回合，换附件重放及 v1 夹带附件被拒绝。

Core 覆盖分块群/发言人/请求/引用绑定、缺少 @、跨群引用、上传过程中撤销授权、群回合及群图片回复链路。BotCore 覆盖原消息查验、100 MB 元数据边界、超限和错误文件、未开启群拒绝、没有额外文字时仍发起文件请求，以及原私聊读取方式。仅 QQ、上游模型与外部传输使用隔离夹具，没有向真实群发送文件或消息。

接口依据已核对 NapCat 官方源码：[GetMsg](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-onebot/action/msg/GetMsg.ts)、[GetFile](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-onebot/action/file/GetFile.ts)。文件内容解析取决于智能体能力，本次只实现收件和受限附件读取，不增加办公文档解析器或群工作区权限。
