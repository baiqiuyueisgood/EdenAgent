## 当前源码确认

- `packages/runtime-pi/src/process-runtime.ts` 仍使用 15 秒心跳期限、60 秒启动期限和 2 秒取消确认期限。运行子进程发送 1 秒心跳。
- 子进程 `ProcessEventStream` 已在 IPC 前采样，并限制为一个在途批次及一个待发快照；每批收到宿主确认后才继续推进持久边界。它仍对原始 delta 调用 `structuredClone`，每 32 个更新才主动让出事件循环。
- 宿主 `StreamCoalescer` 对已采样批次立即提交；该分支不会经过报告引用的 `% 32` 让出逻辑。宿主未采样分支与子进程原始采样分支必须分别分析，不能按“一条固定路径每 32 次写库才让出”解释全部现场事件。
- `StreamPersistence` 已有磁盘增量格式与每 128 层重新快照的边界；不是没有增量存储。不过编码前会序列化比较 `partial` 与 `message`，并序列化比较补丁／全文大小，提交后仍复制完整消息作为基线。
- **当 `partial` 与 `message` 不一致时，编码直接返回原 payload，退回全文保存**；包括字段差异，也可能包括 JSON 键顺序差异。客户机大量全文行是否命中此分支需要检查原始载荷，不能仅从文件体积推定。
- 当前事件表从初始 schema 就有 `UNIQUE(session_id,seq)` 自动索引，并另有两项会话／类型索引。`MAX(seq)` 不能被描述成默认全表扫描。
- 数据库仍使用同步 `DatabaseSync` 与 WAL／`synchronous=FULL`；同步持久化确实可能阻塞事件循环，但客户机各阶段实际耗时尚无测量。

## 报告需要纠正的内容

1. 报告列出的 12 次中断中，只有 **8 次明确为心跳超时**，3 次是 aborted，1 次是取消确认超时。`turns.state=interrupted` 是中断状态，不是心跳误杀的专属原因。
2. 两条更新的 `created_at` 相隔 46 秒，不等于事件循环同步阻塞 46 秒；还可能包含模型等待、进程调度、内存回收或上游事件间隔。需要主／子进程事件循环延迟及复制、编码、提交耗时，与心跳时序关联。
3. 每次更新里的 `message` 通常是当前消息，不是整段会话全文；单条回复增长、累计会话增长和历史恢复开销需要分别测量。
4. CoreBridge 的正常请求不能排除模型供应商请求、流连接及代理故障；Electron network service 的崩溃信息也不能单独证明 Node 事件循环卡顿。
5. 直接将 WAL 的 `FULL` 改为 `NORMAL` 并非无损优化。SQLite 官方明确：NORMAL 保持一致性，但断电或系统崩溃可能回滚已提交事务；不能把这称为与 FULL 完全相同的持久保证。尤其需要保持执行审批与审计的持久边界。
6. 自动删除事件或执行 VACUUM 不是首要修复。事件兼有历史、回放、增量基线和审计用途；删链或重排可能破坏恢复，VACUUM 本身也需要专门维护窗口和资源预算。

官方依据：[SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)、[SQLite 查询优化说明](https://www.sqlite.org/optoverview.html#the_min_max_optimization)。没有把官方文档的一般规则当作客户机已经发生的证据。

## 独立验证

使用随附 Node 22.23.1 和独立内存数据库／临时子进程，不使用用户数据库：

- 运行 `EXPLAIN QUERY PLAN SELECT COALESCE(MAX(seq),0)+1 FROM events WHERE session_id=?`，得到 `SEARCH events USING COVERING INDEX sqlite_autoindex_events_2 (session_id=?)`。
- 在相同消息 ID 下追加 48 次合成更新，分别使用 330,000 和 2,000,000 个 ASCII 字符的正文作为前缀，每次只增加一个字符。正常分支的磁盘 JSON 为 **31,694,016 → 340,889 字节**、**192,013,920 → 2,010,801 字节**；48 次 append 合计约 118／662 ms，单次最大约 20／46 ms。
- 同样的 330,000 字符正文，仅给 SDK `partial` 多加一个字段，48 条全部退出压缩分支：**31,694,976 → 31,694,976 字节**，没有缩减。这里复现的是全文回退机制，不是客户机 15 秒中断。
- 心跳对照：独立健康子进程每 20 ms 发心跳，宿主按 300 ms 期限监督，再单独让宿主同步阻塞 1,000 ms。该次实验仍正常收到子进程回复，**没有复现误杀**。宿主暂停并不必然导致当前看门狗误判；事件循环阶段与 IPC 消息处理次序影响结果。该缩短期限实验不能替代客户机的默认 15 秒现场验证。
- `Server/tests/stream-persistence.test.ts` 与 `Server/tests/unit/sessions/stream-coalescer.test.ts`：**10 项全部通过，0 失败、0 跳过**。覆盖增量磁盘／准确回放、兼容回退、事务失败、隔离消息基线和流式采样边界，未覆盖 MB 级真实磁盘压力下的长时间停顿。

内存数据库没有真实磁盘 fsync 开销，因此不能拿上述毫秒数估计客户机磁盘提交耗时，也不能据此否认客户机发生的中断。

## 后续修复优先级

先确认客户机各流式类型中增量格式、快照和原文回退的数量与体积，并比较不匹配字段；同时增加主／子进程事件循环延迟、IPC 批次确认、复制／编码／提交耗时的有界诊断。然后减少原始 delta 的全文复制与序列化、处理 SDK 字段差异且保留完整恢复语义、按实际耗时让出事件循环，并使看门狗能区分宿主处理滞后与子进程失联。磁盘批量提交需要继续遵守事件先持久化再广播，以及审批／工具副作用审计边界。

提高心跳期限只能作为缓解；不能把“延长到两分钟”作为本问题的唯一修复，也不应直接全局降低事务持久等级或裁剪现有客户数据。本轮只完成复核，相关实现仍待后续授权的修复任务。
