# QQ 智能体普通文件收发提高至 100 MB

2026-10-14，按用户要求将单文件上限改为 100 MB，统一按十进制的 100,000,000 字节计算。此项属于尚未发行的源码改动，已发布 1.11.6 主包及 QQBot DLC 归档保持原大小与摘要。

## 实现

- Agent 在 `packages/api/src/qq-files.ts` 中统一普通文件大小、Base64、JSON 元数据余量、四文件输入预算及传输期限。工作区发送仍仅接受审批后的普通相对路径文件，并校验工作区和接收者。
- Mon 内部 Blob 存储支持 100 MB 普通文件；QQ 私聊的附件暂存、持久队列、读取与重启后重新提交使用对应输入预算。普通 App 上传与输入继续使用原有预算，图片保持既有范围。
- QQ 的签名 HTTP 上传使用按上限推导的编码请求预算和五分钟等待，并限制同时进行的大文件上传。桌面文件发送给 Core 的单独请求允许六分钟，其他 Core 请求默认三十秒不变。
- Core 统一普通文件 REST 上传、QQ 分块接收、上传 Agent、回传下载和发送回执的 100 MB 上限；JSON 请求含有界元数据余量。普通大图片文件作为二进制附件处理，不把大文件内容直接展开为模型图片。
- BotCore 同步 NapCat 本地普通文件缓存读取、文件事件元数据及出站分块校验；文件 API 单独等待五分钟，完成或失败后清理临时文件。
- 四文件、三十分钟暂存、个人超级管理员私聊、群聊边界、SHA-256 校验、审批、账号隔离与未知结果不自动重发规则保留。未改数据库 schema、IPC 版本或产品版本。

## 验证

249 项相关自动测试通过：Agent 39 项、Core 184 项、BotCore 26 项。Server 类型检查通过；架构门禁扫描 1,113 个源码文件，0 个阻断错误，已有规模提醒保留。

主要证据：

- Agent 使用客户包自带 Node.js 22.23.1，在本地签名 HTTP 上实际上传 100,000,000 字节文件，暂存并交给运行时处理，经审批从工作区回传，核对长度与 SHA-256。验证普通 App 输入仍受原 32 MiB 总量约束，QQ 四文件预算可以处理 100 MB 附件；100,000,001 字节即使 Base64 长度与边界相同也被拒绝。
- Core 使用自身虚拟环境运行全部隔离 QQ 契约，验证 100 MB REST 发送、入站分块重组、超限元数据与请求体拒绝、管理员和目标权限、坏回执及未知结果不重发。测试入口采用正式 `api/devices/qq_bot/` 前缀，文件投递模块已纳入默认契约入口。
- BotCore 使用 BotLauncher 自身虚拟环境和临时状态入口，验证 NapCat 普通文件缓存读取、100 MB 临时文件上传、完整分块重组、错误校验和拒绝、临时文件清理，并回归图片与长回复行为。OneBot 调用为模拟接口，不是实际 QQ 收发。
- 首轮检查发现存储预算组装使 `createServices` 复杂度超标，已提取职责明确的预算函数；桌面回归发现 Mon 客户端还限制最多 180 秒，已配套允许单次文件请求等待 360 秒，普通请求默认 30 秒不变，取消行为仍通过。初轮日志保留，修正后的检查均通过。

证据保存在根工作区 `.release/qq-file-100mb-20261014/`，包括 `agent.log`、`core.log`、`bot.log`、`types.log`、`architecture.log` 及完成记录。夹具仅使用临时目录、内存数据库、本地 HTTP 和模拟 OneBot；不访问真实用户数据库，不向实际 QQ 联系人发消息。真实 QQ 文件收发及客户机器大文件体验仍待现场验收。

## 部署状态
