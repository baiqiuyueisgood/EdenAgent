## 临时目录与启动周期

实际 Ubuntu 为 26.04.1 LTS，`/tmp` 是 tmpfs。Eden 的 `runWslCommand` 每次创建新 shell，没有清空 `/tmp` 的代码；发行版停止／重新启动时，内存挂载内容可能丢失。因此只看源码未发现清理，并不足以否定这次会话的文件丢失。

systemd journal 保留了不同 boot ID 的启动周期，分别覆盖 04:06:23–04:07:10、04:09:19–04:10:59、04:11:16–04:14:17；当前 boot ID 的最早 journal 记录为 04:15:34，当前 `/tmp` 挂载创建时间为 04:17:36。说明执行期间确实经历过多个启动周期。发行版生命周期与 tmpfs 重新挂载可以解释文件丢失；没有保留每条命令结束时的发行版状态或触发停止的完整记录，尚不能把所有重启精确归因于空闲停止。

核查期间多次独立只读调用的 boot ID 与 `/tmp` 设备／inode、创建时间一致，未出现每条调用重新挂载。另有数条命令主动执行 `rm -rf /tmp/st`，这些命令自身也会清理它的临时脚本目录。

## 已确认的宿主与命令问题

1. `packages/execution/src/wsl-command.ts` 的发行版枚举固定 5 秒超时，任何错误都转换为空列表；执行入口随即报“发行版不可用”。两次真实失败的原因被此处丢失，不能区分未安装、枚举超时和系统错误。约 6.4／6.6 秒的整次工具耗时与预检查超时相容，但原始异常已被吞掉，不能直接认定具体原因。
2. `packages/execution/src/process-runner.ts` 对 stdout／stderr 固定使用 UTF-8。实际读取 WSL 的原始 stderr 后确认，该次警告为 UTF-16LE，内容为“检测到 localhost 代理配置，但未镜像到 WSL。NAT 模式下的 WSL 不支持 localhost 代理。”原审计返回因此混入 NUL 与乱码。该警告出现时退出码仍是 0，不等于命令执行失败。
3. 多条命令使用 `node ... 2>&1 | grep ...` 或 `| tail ...`，shell 退出码取末尾程序的状态。04:10:17 的 ESM 错误及后续脚本异常都伴随 `exitCode: 0`，工具标为完成。Eden 当前按 shell 退出码判定结果，没有解析 stdout 中的错误；命令编写需保留被测程序的失败退出码。
4. `systemd=true` 已设置，PID 1 为 systemd；当前状态 `degraded`，失败单元为 `systemd-binfmt.service`。它与现有 HTTP 服务可访问同时存在，不能仅凭 degraded 宣称 8123 不可用，也不能据此确认服务已托管。

## 后续处理建议

优先保留并分类发行版探测错误，修正 WSL 诊断编码，向模型明确每次 shell 的状态边界及临时目录生命周期。跨调用所需的脚本和工具应放在持久目录，明确 `.cjs`／`.mjs` 或项目模块类型，避免管道掩盖程序退出码。

长期服务应拥有宿主持久进程记录、状态／日志／停止入口和 Windows 侧健康检查；启动失败或结果未知时先核对现存进程，再决定是否重试。systemd 开启、后台进程启动成功、Windows 当前访问成功与电脑重启后自动恢复是不同验收项。本轮仅完成实际情况核查，没有修改执行实现或自启配置。
